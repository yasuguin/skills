# grill-visual

grilling の質問のうち、視覚で判断してもらうものをブラウザに出すための companion。localhost のサーバーが案の HTML を出し、ユーザーのクリック・補足・コメントを `.grill-visual/` のファイルに書く。

サーバーは Node 標準だけで動くローカル完結のもので、`127.0.0.1` だけで待ち受け、外部へのリクエストは一切しない。HTML の書き方と CSS クラスの一覧は [references/screen-pattern.md](references/screen-pattern.md) が正本。

## いつ使うか

質問 1 つごとに判断する。セッション単位で「ブラウザモード」に入らない。

- **ブラウザに出す**: mockup / wireframe、レイアウトの並列比較、ナビゲーション構造、構成図・データフロー・状態遷移図、色や余白のような look and feel
- **grilling の通常の質問で聞く**: 要件・スコープ、文章で書ける A/B/C、トレードオフ表、API や data model の選択、clarifying question

UI が話題でも視覚の質問とは限らない。「どんなウィザードにしたいか」は概念なので通常の質問、「この 3 つのウィザード配置のどれか」は視覚なのでブラウザ。

## 見せ方: ユーザーの既定ブラウザに `open-url` で出すだけ

案はユーザーが自分のブラウザで見て選べば足りる。ブラウザ自動操作で案のページを開いたり、スクリーンショットを撮って確かめたりしない(操作の往復とトークンを払うだけで、ユーザーの判断材料は増えない)。

- **クリック記録が要らない軽い比較**(実装後の手直しで 2〜3 案を並べる等): 案を並べた HTML 1 ファイルを OS の一時ディレクトリに書き、`open-url <絶対パス>` で開いて、案を文章で聞く。サーバーは立てない。画像は data URI で埋め込めば file:// でも表示できる。
- **grilling のラウンドで何画面も続ける・クリックで選ばせる**: 下の手順でサーバーを立てる(最初の画面を書いたら `open-url` で開く)。

## 手順(サーバーを立てる場合)

1. **提案は最初の視覚質問が出た瞬間に、それ単独のメッセージで**。grilling のラウンドの冒頭で先回りして提案しない。断られたら以後はテキストだけで続け、ユーザーが言い出すまで再提案しない。
2. **起動**。承認後に `bash scripts/start.sh --project-dir <repo root>` を実行し、返ってきた JSON の `url` / `screen_dir` / `state_dir` を控える。スクリプトが `error` JSON を返したら、ログ(`state_dir/server.log`)を読んで原因を直す。URL を渡す前に `curl -s -o /dev/null -w '%{http_code}' <url>` で 200 を確かめる。`url` の `?key=` は認証キーなので削らずに丸ごと渡す。`.grill-visual/` を対象リポジトリの `.gitignore` に入れるよう促す。起動の詳細(`--foreground`、自動停止)は references を見る。
3. **1 画面 = 1 ファイル**。`screen_dir` に `layout.html` のような意味のある名前で content fragment を書く(`<html>` 不要、frame が包む)。ファイル名は再利用せず、修正版は `layout-v2.html`。heredoc ではなくファイル作成ツールで書く。
4. **ターンを終える**。最初の画面を書いたら `open-url <url>` で開き、その出力を報告に載せる(サーバーはブラウザを開かない)。2 画面目からは開いているタブが自動で切り替わるので開き直さず、URL を毎回添え、画面の要約 1 行と「選んだら右上の『指示をコピー』で貼ってください(案への補足・要素へのコメント・微調整も一緒に載ります)」を書いて待つ。推奨がある問いは、推奨の選択肢に `data-recommended` を付ける(frame が「推奨」の印を付け、初めて開いたときに選んだ状態にする。変えたい行だけ押せば済む)。問いが複数ある画面は、選択肢の入れ物に `data-question` を付けてコピーの行を問いの名前にする。角丸・余白・色のように数値で詰めたい見た目は、`data-tweaks` の中に `input` を置いて右上の操作バーの下に浮かぶ微調整パネルで動かせるようにする(書き方は references)。
5. **次のターンで `state_dir/instruction.md` と `state_dir/events` を読む**。instruction.md はコピーされる指示文の最新版で、ユーザーが画面を触るかコピーしたときだけできる(貼り忘れ・貼った後の手直しを拾える)。events は JSONL のクリック履歴。ユーザーの返答を主、instruction.md を従、events を補いとして合成する。どちらも無ければ操作していない。
6. **視覚の質問が終わったら待機画面を出す**(`waiting.html`)。解決済みの選択肢を見せ続けない。
7. **終了時は `bash scripts/stop.sh <session_dir>`**。`--project-dir` 付きなら画面は `.grill-visual/` に残る。

## 画面を書くときの規律

- 1 画面に選択肢は 2〜4 個。画面の先頭に「何を判断してほしいか」を書く(「どれか選んで」ではなく「どのレイアウトが業務向けに見えるか」)。
- 忠実度は質問に合わせる。配置の質問は wireframe、仕上がりの質問だけ作り込む。
- mockup の中身は、グラデーションや装飾ラベルに頼らず、余白と文字の大きさで階層を作る。frame(`scripts/frame-template.html` と `scripts/companion-ui.js`)の見た目は mockup 側で上書きしない。
- 実データが判断を左右する題材(写真主体のページ等)は placeholder ではなく実データを使う。
- 構成図・データフロー・状態遷移図の案は、ノードと接続線で描き、観点ごとに図を分ける。
- **導線・ナビゲーションの質問は体系ごとに出す**。タブを残すか消すかのような部品単位の比較ではなく、ホーム・メニュー・タブ・FAB・画面内リンクに何を置くかの一式を 1 案とする。各案には、ナビゲーションマップ(画面と遷移の図。各画面の左上・右上に何を置くかも書く)と、主要な行き先ごとに起点から何タップで届くかの到達表を両方付ける。体系が決まるまで要約・実装へ進まない。手順は [references/navigation.md](references/navigation.md)。
- **作る機能の UI を一通り見せるときは、使い方の流れ 1 本を 1 枚に通す**。画面を部品ごと・案ごとに別ファイルへ分けず、冒頭に流れの全体(入口 → 共通の到達状態 → 操作 → 結果)を並べ、その順に番号付きの画面を空の状態から結果まで置く。入口が複数あれば、どれも同じ到達状態に行き着くことを見せる。判断が要る画面だけに「判断してほしいこと」と案の並列を置き、残りは「このままでよいか」を 1 問にまとめて聞く。手順は [references/flow-proposal.md](references/flow-proposal.md)。
- **判断の基準を決める質問は、YES / NO で 1 つの答えに行き着くフローチャートで出す**。条件の箇条書きや表だけで見せず、図の下にたどり方の例の表を添える。線が箱を横切る・ラベルが重なる・端で切れる配置は避ける。決まったチャートを docs に残すときは Mermaid にする。
- 出した案は OS の一時ディレクトリに置く。ユーザーが残したいと言ったときだけ、対象リポジトリの `docs/design/<題>/` に番号順で置き、各画面の問いと決まったことを `README.md` の表にまとめる。

## 前提にしている skill

質問の出し方(ラウンドの進め方、1 問ずつ聞くこと、推奨を添えること)は、Matt Pocock の [`grilling`](https://github.com/mattpocock/skills)(mattpocock/skills、MIT)に従う。この skill はその考え方に乗り、視覚で判断する質問だけを足すもので、grilling の中身は写さず、名前で呼ぶだけにしている。用語や判断を文書に残す `grill-with-docs` も同じ repo の skill で、画面で決まったことはその流れで記録する。

入っていなければ `npx skills@latest add mattpocock/skills --skill grilling --skill grill-with-docs` で入れる。
