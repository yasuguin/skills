# rule 追加前の誤検知チェックリスト

`deny_patterns` を書いたら、そのまま登録せずこのチェックを行う。

## 手順

1. 禁止したい実際のコード例を1つ書く（deny側が確実に検出できることを確認する材料）
2. **禁止パターンと表面上似ているが許可すべき正当なケースを最低1つ挙げる**。既存の
   禁止の理由を書いた文書（デザインの規約や、rule の `skill` 欄が指す skill）に「禁止しないもの」があれば、まずそこを読む
3. 2で挙げたケースが `deny_patterns` に誤って引っかかるかを実際に試す
4. 引っかかるなら `allow_patterns` に追加し、引っかからなくなるまで詰める
5. `allow_patterns` を強くしすぎて deny 側の検出力が落ちていないか、元の違反例で再確認する

## 過去に見つかった誤検知の実例

- **矢印 `→` を絵文字扱いしてしまう**: 絵文字禁止ルールの初期実装で `U+2190-21FF`
  （矢印ブロック）まで対象に入れてしまい、`python foo.py → uv run foo.py` のような
  技術文書の表記を block してしまうところだった。矢印レンジを最初から対象外にして解決した
- **`mask-image: linear-gradient(...)` のフェード演出**: `ui-no-gradation` rule の禁止対象
  `linear-gradient` は、可読性のためのフェードマスクにも使われる。同一行に `mask-image` /
  `-webkit-mask` / `mask:` が含まれる場合は `allow_patterns` で除外する
- **`rg 'linear-gradient'` のような検索コマンド自体の誤爆**: UI系の禁止パターンを
  Bash コマンド文字列にも適用すると、違反を探すための検索コマンド自体を block してしまう。
  `ui-banned-pattern.json` は Write/Edit/NotebookEdit の書き込み内容だけを対象にし、
  Bash コマンド文字列は対象外にすることで回避した

## 迷ったときの判断基準

- 正当なケースが1つも思いつかない → そのまま `allow_patterns` 無しで登録してよい
- 正当なケースが思いつくが例外化しやすい（同一行に特定のキーワードが伴う等）→
  `allow_patterns` で対応する
- 正当なケースと違反が同じ見た目で区別できない（例: デザインシステム承認済みの
  グラデーションと勝手に足されたグラデーションが構文上同一）→ hook化を諦め、
  既存skillの人手レビューに委ねる。無理に registry へ入れない
