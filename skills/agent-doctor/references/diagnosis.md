# 指標の読み方と疑うルール

`analyze.py` の出力の節ごとに、何を見て、どのルールを疑うかを書く。数値の目安は 2026-10-13 の
初回診断（直近 7 日、ターン 75h）の実測で、絶対的な基準ではない。前回比での増減を重く見る。

## 目次

- 自動で見つけた異常

## モデルの応答とコンテキスト

- main の Opus がターン時間の 3 割前後を占めるのは普通。問題は 1 回あたりの「最初の出力まで秒」で、
  コンテキストが大きいほど伸びる。初回診断では p50 17 万・p90 54 万トークンで、最初の出力まで平均 5.8 秒。
- 「セッション開始時 p50」は CLAUDE.md・rules・skill 一覧などの固定分。ここが増えたら、指示ファイルか
  自動 trigger の skill の description が増えている。
- 作業中に膨らむ分は、長い会話を続ける運用が原因。grill から実装まで同じ会話で進める進め方の行
  （AGENTS.md の進め方）や、`/compact` / `/clear` の使い方を疑う。
- Haiku は Opus より 2 倍以上速い（出力 tok/秒）。実装を安いモデルに寄せるのは速度にも効く。

## Bash とテスト

- 「単純なコマンド」の p50 が 1 秒前後なら、hook や権限確認の固定オーバーヘッドは小さい。数秒あるなら
  PreToolUse hook の遅さを疑う。
- `test` / `lint/type` の合計と、遅い Bash の上位を見る。10 分を超える回があれば、全量の typecheck・
  テストを回しているか、e2e を繰り返している。

## 自動で見つけた異常

集計の冒頭に、しきい値を超えたものだけが並ぶ（判定は `analyze.py` の `find_anomalies`）。報告では、これを最初に全件扱う。
分類別の平均（「git/gh」など）に埋もれる遅さを拾うための欄で、2026-10-29 に、ある repo の pre-commit が 104 秒・
pre-push が 76 秒かかっていたのに、「git/gh 平均 12 秒」の中に隠れて気づかれなかったので足した。

直す前に、集計の期間の中に、その hook や script をすでに直した commit が無いかを `git log` で見る。あれば、生ログの
所要時間を 1 時間ごとに切って、その commit の前後で比べる。7 日の集計は直す前の分も数えるので、直したものが
次の週まで異常に出続ける。2026-11-04 の集計では、ある Stop hook の 3 件（Stop 平均 3.0 秒、Pre/PostToolUse の
p90 36〜51 秒）がすべて 10-29 の高速化 3 commit より前の記録だった。後は Stop 平均 0.4 秒で、数十秒は 1 件も無かった。

- **本来すぐ終わる `git commit` / `git push` / `git add` などの中央値が 10 秒超**: 本体ではなく、
  git hook（`.githooks`・`.husky`・lefthook）や、コマンドが呼ぶ script・テンプレートが重い。どの repo かは、生ログの
  `cwd` で分けて確かめる。`git add … && git commit` と続けて打つと、commit の hook の時間が `git add` 側に数えられる。
  hook の中の検査を 1 つずつ `time` で測り、桁違いの 1 つを探す（ある repo では 9 つ中 1 つが 104 秒、残りは 4 秒以下だった）。
  直し方は、検査を変更のあった範囲だけに絞るか、遅い 1 本を速くする。hook の why コメントにある「約 N 秒」は、テストや対象が増えると
  古くなるので信じない。
- **hook がタイムアウト（600 秒）に達した**: 1 回でも、その間ターンが止まっている。ロック待ち・ネットワーク・入力待ちと、
  入力の大きさに比例して外部コマンドを起動する作り（行 × パターンごとに `grep`）を疑う。生ログで
  `attachment.durationMs` が 590000 以上の行の `toolUseID` を探し、その tool_use の `input` を
  `{"tool_name", "tool_input", "hook_event_name", "cwd"}` に組み直して hook の標準入力へ流すと再現できる
  （2026-10-29、ui の banned-pattern hook が 154 行の e2e spec で 60 秒を超え、行 × パターンの `grep` が原因と分かった）。
- **毎回動く hook の平均が 2 秒超**: ツール呼び出しのたびの固定費。1 件ずつ subprocess を起こす処理（`git show` を
  ファイルごと、`lsof` / `ps` をプロセスごと）を探し、まとめて 1 回で取る形にする。

## hook

- Bash 1 回の固定費（単純なコマンドの p50）は、同じイベントの hook が並列に動くので「一番遅い hook」で決まる。
  `scripts/measure_hooks.py` で、Bash に当たる PreToolUse / PostToolUse / Stop を `cat` 程度の入力で 1 本ずつ測る
  （2026-10-29、Stop hook の 1 本だけが 3 秒台で、残り 12 本は 0.2〜0.8 秒だった）。
- 測る前に `uptime` でロードアベレージを見る。並列セッションのテスト（vitest のワーカー）でコア数の 4 倍を超えると、
  git 1 回が 0.6 秒から 7 秒になり、新旧の比較が揺れで逆転した。比べるときは時間でなく、起動した子プロセスの数
  （`python -m cProfile` の `subprocess.run` の回数）を数える。hook を一時ディレクトリへ写して比べるときは、隣の
  モジュールも一緒に写す（写し忘れると import で即終了し、速く見える）。
- 「エラー」が多い hook は、動いていないのに気づかれていない。macOS の `/bin/bash` は 3.2 で、
  `mapfile`・`declare -A` などは動かない。生ログの `stderr` を見て原因を確かめる。
- 平均が 1 秒を超える PreToolUse hook は全ツール呼び出しに効く。まれに数十秒かかる hook は、
  uv の初回起動やロック待ちを疑う。

## Stop hook の block

- block 1 回ごとに、大きなコンテキストの主エージェントが 1 往復する。合計回数と、ack の回数・理由を見る。
- ack の理由が「作業途中」「別セッションの変更」「無関係な CI」ばかりなら、その指摘は block する価値が
  ない。指摘の ID の作り方（内容込みだと編集のたびに再通知になる）や、対象の絞り方を疑う。
- 「検査失敗」は hook 自身の失敗。gh のアカウント違い（404）や git のロック待ちなど、原因ごとに直す。

## ガードに止められた回数

拒否や失敗の 1 回ごとに、主エージェントが言い換えか回避の 1 往復をする。同じ理由が並ぶのは、ルールの
置き場所か書き方の問題。ルールを機械的な強制（hook・permissions・lint）へ移すか、書き方を直す。

- 「hook の拒否」で同じ理由が続くなら、まず誤検出を疑う。生ログで止められたコマンドを見て、禁止語が
  commit メッセージ・grep の検索語・heredoc の本文に説明として書かれていただけなら、hook の照合範囲の問題。
- 「classifier の拒否」が `Self-Modification` なら、自己設定の変更をユーザーが具体的に指名していない。
  変更する項目そのものを示して選んでもらう手順になっているかを見る。
  同じ操作が繰り返し止まるなら、permissions の狭い allow ルールへ移せないか検討する。

## 委譲

- サブエージェントの型ごとに、回数・平均秒・実際のモデル・出力 tok が出る。型の設定（model・effort）を変えて試すときは、
  この表の前回比で続けるか戻すかを決める。
- 委譲の往復コストは「サブエージェントへの指示を書く時間」と「納品通知で始まるターン」の合計。納品通知のターンが長いなら、
  納品ごとに検証を回していないかを見る。


## 質問

- 「回答待ち」はユーザーの時間なので遅さではないが、質問 1 回ごとに主エージェントが 1 往復する。
  1 セッションで数十問なら、質問の粒度のルール（AGENTS.md の伝え方、`grilling` の運用注記）を
  疑う。
