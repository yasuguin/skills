# worker の力量の目安(実測)

task の大きさと、task にどこまで細かく書くかを決めるための観察。agent の種類によって rule・完了条件・レビューの基準は変えない
(SKILL.md の原則)。ここに書くのは「1 task をどこまで割るか」「task で何を名指しするか」の目安だけ。
観察はモデルと確かめた日を付けて足していき、モデルが変わったら測り直す。

## pi(openai gpt-6-luna、medium) 2026-10-18

ある Web アプリの repo で 10 回ほど投函して分かったこと。

- **範囲が広いと、手を付けずに「未着手」でブロックする。**
  - 例: 9 つのゴールを持つ画面の task(Session 一覧・チャット・入力欄・vendor 10 ファイル)、「必要なファイルを vendor して」
  - 効いた対処: 必須テスト 2〜3 本の task に割り直す(B1 / B2a / B2b / B3)
- **最初の障害で止まる。**
  - 例: `pnpm init` の `devEngines` による pnpm の自動ダウンロードが sandbox で失敗した、`ERR_PNPM_IGNORED_BUILDS`、`runAgentLoop` の import 先の読み違い(「subpath だけ」を別のパッケージにも当てた)、テストの日付が ISO 形式でない
  - 効いた対処: task に「最初の障害で止めない」「迷ったら単純な方」と書く。依存の install は orchestrator が先に済ませる
- **実装は入れても、指定したテストを書かずに返す。**
  - 例: SSE・履歴・失敗の受け入れテスト 5 本が作られないまま
  - 効いた対処: テストの部品とコードの例を task に書いたら書けた(pi-ai の faux provider で偽の LLM を作る例)
- **報告は正直で、やっていないことはやっていないと書く。**
  - 例: 「RED→GREEN は確認していない」「未着手」
  - 効いた対処: report は信じてよい。ただし `check_delivery` の pass だけで完了とは見ない
- **後片付けを忘れる。**
  - 例: dev server(ポート 5173)を握ったまま pane が終わった
  - 効いた対処: レビューのときに orchestrator が止める

効いた task の形:

- 1 task = 必須テスト 2〜3 本。写すファイル、API の形、テスト名、ログのパスを名指しする。
- 前回のブロックへの「裁定」を冒頭に書き、続きの task は同じ pane に投函する(文脈が健全な間)。
- 残った小さな仕上げ(判断の要らないテストの補い、format、lint 1 件、テストデータの誤り)は、差し戻すより orchestrator が直す方が速かった。
  範囲は SKILL.md の「orchestrator が自分でやるのは」の目安に従う。

## codex

- 判断の多いライブラリの model の操作は、worker に割らない。codex の worker に判断の多いライブラリの model の編集を割ったところ、
  小さく割っても止まる・未着手で返す、が続き、主のエージェントが自分で書いた方が速かった。

## 役割の組み合わせの例

- 実装: `implementer` に任せる → orchestrator が diff を精読し、検証の記録と照らしてレビューする
- 原因調査: `investigator` に任せる → orchestrator が仮説を疑ってかかってレビューする → 修正は新しい `implementer` に投函する
- 大きめの変更: `implementer` → 独立した `reviewer` でもう 1 往復 → orchestrator が最終判定する
- 受け入れの確認だけ: `verifier` に任せる → orchestrator が結果を裏取りして報告する

## task の性質で worker の格を選ぶ

- 軽い worker(pi など): 仕様が固まった機械的な作業、原因まで分かっている修正
- 上位の worker(claude など): 状態や競合を含む UI、設計の判断が残るもの、基盤やランタイムに絡むもの

  基盤・ランタイム・外部サービスの挙動に不確かさがある ticket は、実装の前に investigator で切り分ける。

- **agent の種類やモデル名で、rule・完了条件・検証・レビューの基準を変えない**。変えてよいのは、1 task に詰める量と、task にどこまで細かく書くかだけ。
  上位の worker は必須テスト 5〜8 件程度、軽い worker は 2〜3 件程度を目安にし、大きい ticket は前半と後半(A・B1・B2a のように)に分けて順に投函する。
  worker が「未着手」や一部だけのブロックで返してきたら、同じ task を投函し直さず、さらに小さく割って出し直す。
  モデルごとの実測の目安は、このファイルの上の節。
