# 機能の UI を流れごと見せる提案の進め方

「作ろうとしている UI を全部見せて」のように、機能の使い方を通しで確かめたい依頼では、画面を部品ごとに比べても判断が進まない。どの入口から入り、どこで何を選び、送った後に何が起きるかが分からないと、個々の画面の良し悪しを決められないため。流れ 1 本を 1 枚の HTML に通し、判断が要る画面だけを選ばせる。

## 手順

1. **流れを先に書き出す**。入口(ボタン・ドラッグ・別画面のメニューなど)、入口が行き着く共通の状態、そこからの操作、結果の画面を並べる。入口が複数なら、どれも同じ状態に行き着く形にそろえる(行き着く先が違うなら、それ自体が先に決める問い)。
2. **冒頭に流れの全体を 1 行で置く**。入口ごとの短いラベルと、矢印でつないだ「共通の状態 → 操作 → 結果」。読み手がどの画面が流れのどこかを見失わないようにする。
3. **画面を番号順に置く**。空の状態 → 選ぶ → 選んだ後 → 別の入口 → 結果、のように起点から結果まで欠かさない。各画面には「何をする画面か」を 1〜2 文で書き、mockup は実データに近い文言・件数・サムネイルにする(placeholder だと情報量や並びの判断ができない)。ほかの作業で変わりつつある画面(並行中の変更)は、その最新の形で描く。
4. **判断が要る画面だけ案を並べる**。その画面の先頭に「判断してほしいこと」の枠を置き、問いを 1 文で書いて案 1 / 案 2 を横に並べる。各案の下に、選んだときに起きること(読み違えのおそれ・操作の手間)を 1 行で書く。
5. **聞くのは 2 問までにする**。判断が要る画面の案を選ぶ問いと、「残りの画面はこの形でよいか(直したい画面があれば番号で書く)」の 1 問。画面ごとに 1 問ずつ聞かない。
6. **決まったことを記録する**。repo に残すと言われたら `docs/design/<題>/` に HTML を置き、`README.md` に画面ごとの「問い / 決まったこと」の表を書く。案の後で別の決定(DESIGN.md など)と食い違いが見つかったら、表に「案の画面と違う、こちらが正しい」と書く。
