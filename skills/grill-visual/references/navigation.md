# 導線・ナビゲーションの質問の進め方

タブ・メニュー・ホーム・フローティングボタン・画面内リンクのように「どこから何へ移るか」を決める質問は、部品の見た目の比較では決まらない。1 つの部品を選んでも、他の画面からの行き来が後から問題になるため。体系ごとに案を出し、行き来のしやすさを数字と図で見せる。

## 手順

1. **主要な行き先を先に列挙する**。ユーザーの毎日の動き（開いて最初に見るもの、そこから向かう作業）を聞き取り、行き先を 3〜6 個に絞る。たまにしか開かない画面（統計・設定など）は分けて書く。
2. **制約をコードから先に確かめる**。下に固定の UI がある画面（チャットの入力欄、復習の評価ボタン）、横スクロールする要素、PWA の standalone かどうか（端スワイプの「戻る」とぶつかるか）、PC 幅のサイドバーの有無。重ねられない場所に FAB やタブを置く案を出さないため。
3. **体系ごとに案を出す**。1 案 = 「ホーム・メニュー・タブ・FAB・画面内リンクのそれぞれに何を置くか」の割り当て一式。2〜4 案。部品だけを差し替えた案（タブを残す / 消す）を並べない。
4. **各案にナビゲーションマップと到達表を両方付ける**。マップは画面を箱、遷移を矢印にした図で、各画面の箱に左上・右上に何を置くか（メニューボタン・戻るなど）を書き、メニューからの移動と画面内リンク・押し込みの移動を線の種類で分ける。到達表は行 = 主要な行き先、列 = 起点（ホーム、よくいる一覧画面、作業中の画面）、セル = タップ数（「メニュー＋1」のように手段も書く）。表だけでは戻る先や押し込みの階層が見えず、マップだけではタップ数が比べにくいため（2026-10-18 ユーザー決定）。
5. **ユーザーの返答で統合・分割を試す**。行き先どうしをまとめられないか（新規作成と一覧、復習と一覧など）を問い、まとめた後の体系で表を作り直す。
6. **体系が決まるまで要約・実装へ進まない**。戻る先、一覧どうしの横移動、PC 幅、ジェスチャーが効かない場面など、体系から派生する細部を潰してから全体の確認画面を 1 枚出す。
