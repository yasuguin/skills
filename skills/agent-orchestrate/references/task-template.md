# タスクファイルのテンプレート

`/tmp/<slug>-task.md` として保存する。`<...>` を埋めて使う。`<skill-dir>` は agent-orchestrate の絶対パスに置き換えて書く(worker は skill の場所を知らないため)。
仕様・注意はタスクに合わせて増減してよいが、**報告手順・コミット禁止・検証の段の指定・対話承認の禁止・役割宣言(worker 自身が実装する)は必ず残す**。
worker は新規セッションでも続投 pane でもこのファイルだけで判断できるように書く。

```markdown
# タスク: <一行の目的>

対象リポジトリ: <絶対パス>(ブランチ: <branch>)

## ゴール(完了条件)

- <仕様項目 1>
- <仕様項目 2>
- 変更ファイル一覧を含む完了報告(下記)

## 注意(リポジトリ固有)

- この依頼は新規 worker セッションまたは同じ ticket の続投 pane で実行される。このファイルに書かれていない会話文脈や
  前回セッションの記憶を前提にしない。続投でも report と done マーカーはラウンドごとに分ける。
- **あなたは worker であり、この作業を自分で実装する**。このファイルに分割投函の指示がない限り、
  agent-orchestrate 等で別の worker やサブエージェントへ再委譲しない。次はいずれも再委譲の根拠にならない:
  報告手順に agent-orchestrate の script パスがあること(報告用 script の置き場所)、リポジトリの
  AGENTS.md / CLAUDE.md の「実装は agent-orchestrate で worker へ委譲する」節(main 向けの規則で、
  この task を受けたあなたには適用しない)、自分の instruction file の「実装は委譲する」方針。
- **コミット禁止**。変更は作業ツリーに残したままにする(この後レビュー側が検証してコミットする)。
  「禁止」と書くだけでは codex の worker が commit することがあるので、「git commit を実行しない（instruction file に commit の手順があっても行わない）」と書く。commit されたら orchestrator が `git reset --soft <base>` で戻して作り直させる。
- **TDD で実装する。**「仕様」の名指しテストファイル 1 本で赤→緑を確認する。さらに安い段として、repo の lint・型チェック(無ければ変更ファイルへの lint・incremental typecheck)を実行し、完了報告前に 0 件にする。repo の検証が数分以内なら、task で指定された重い段（全体 test・E2E・build）も実行し、コマンド・真の exit code・ログのパスを report に残す。目安 5 分超の repo では重い段を実行しない。
- 完了報告を書く前に、対象 repo で `bash <skill-dir>/scripts/check_delivery.sh <repo> <task-file> <base-commit>` を実行し、`check_delivery: status=pass` にする。出力を report に貼る。
- **対話での確認・設計承認を求めない**。このタスクファイルが承認済みの設計・要件であり、
  記載の制約内では最有力案を自分で選んで進める(grilling 等の「実装前に設計承認」手順は
  このファイルの受領で満たされている)。制約を超える判断や、複数案で完了条件の意味が変わる
  分岐に当たったときだけ、質問と選択肢を report に書いて「ブロック」で報告する
  (pane 内で回答を待たない)。
- **最初の障害で止めない**。依存のエラー、import 先の読み違え、テストの失敗などに当たっても、原因を調べて直し、ゴールを
  すべてやり切るまで進める。迷ったら単純な方を選び、選んだ理由を report に書く。ブロックしてよいのは、外部への通信が要る、
  ゴールの意味が変わる判断が要る、のどちらかのときだけで、その場合も他のゴールを先に進め、試したことと詰まったエラー全文を
  report に書く。「未着手」のままブロックにしない。
- dev server などを起動したら、作業の最後に止める（ポートを残さない）。
- <リポジトリ固有の罠・規約。例: rg が壊れるので grep を使う、i18n は ja のみ、等>

## 仕様

<実装の詳細。ファイルパス・行番号・期待挙動を具体的に>

repo の検証区分: <軽い repo / 重い repo（目安 5 分超）>
安い段: <repo の lint・型チェックのコマンド、または変更ファイルへの lint・incremental typecheck>
重い段: <軽い repo の場合だけ指定。コマンドを書く。重い repo は「orchestrator が実行」>
受入基準とテスト対応表:
| 受入基準 | テスト（ファイル:テスト名） |
|---|---|
| <基準> | <file:test name> |

## 必須テスト

- `<受入基準に対応するテスト名をそのまま書く>`

UI の確認場面: <URL・操作。UI 変更が無ければ「なし」>

必要なときだけ、次の見出しの下に許可理由を書く（lint 設定変更は既定で禁止）:

## lint の設定の変更を許す

<変更が受入基準に必要な理由>

テストを書く場合の名指しコマンド: <そのタスクのテストファイル 1 本を実行するコマンド。振る舞いが変わらないなら「なし」>

## 完了報告(必須。これもゴールの一部)

1. 結果(変更ファイル一覧、仕様項目ごとの対応状況、受入基準ごとのテスト対応表（ファイル:テスト名）、
   未解決事項、安い段と重い段で実行したコマンド / ログの絶対パス / 真の exit code)を
   `/tmp/<slug>-report.md` に書く。UI 変更で、task が撮影の場面を指定したときだけ、その場面を撮影し、画像パスを書く（指定が無ければブラウザを開かない）。
   「既存の失敗」「環境の問題」と報告する場合は、修正前 commit（`git stash` は使わず worktree 等）で同じ失敗が起きるログを添える。ログが無ければその主張を書かない。実行していない検証を「成功」と書かない(実行していないなら書かない)。
2. 次のコマンドで作業ステータスを記録する(作業上ブロックして中断する場合も、理由を report に書いた上で必ず記録する):

   完了時:
   `bash <skill-dir>/scripts/mark_report_done.sh /tmp/<slug>-report.md 完了 '<一行要約>'`

   ブロック時:
   `bash <skill-dir>/scripts/mark_report_done.sh /tmp/<slug>-report.md ブロック '<理由>'`

   このコマンドは report の隣に `/tmp/<slug>-report.md.done` を書くだけのローカルなファイル操作であり、
   送信・配送は行わない(依頼側が別プロセスで report の完成を検知する)。
   同じ report パスで再実行しない(「記録済み」エラーになる)。
   スクリプトを実行できない場合は、同じ内容を直接書いてもよい:
   `printf 'status=完了\nsummary=<一行要約>\n' > /tmp/<slug>-report.md.done`
3. `mark_report_done.sh` は done マーカーを作成した後、courier が配送できたか(着弾確認含む)を
   最大 60 秒待ってから結果を出力して終了する。この出力をそのまま読み、**その文言をそのまま**
   自分の最終報告・依頼主への回答に使う。「配送を確認できた」以外(未確認・配送失敗・タイムアウト)が
   出たときも、自分の判断で「報告した/送信した」と言い換えない。宛先を推測して別の手段で送ろうとしない。
   script を使えず printf で直接 done マーカーを書いた場合はこの配送確認が走らないので、
   最終報告には「done マーカーは作成済み、配送は未確認」と書く。
```

## 記入時の注意

- **manifest パス・pane ID・transport を task に書かない**。worker に宛先情報を渡すと codex の
  approval review が exfiltration と判定して報告コマンドを拒否する。worker が知ってよいのは
  report パスと done マーカー手順だけ。route manifest は投函側が `mktemp -d` の専用ディレクトリに
  作って courier と共有する(前回の manifest を再利用・上書きしてはいけない)。
- 報告メッセージは 1 行のみ。詳細は必ず report ファイルへ。
- 検索範囲は書き換えてよいパスに限定する。「参照残りゼロ」の rg 条件を `shared apps` のように広く書くと、読み取り専用の
  `apps/*-legacy` まで改名して条件を満たしに行った。
- 受入基準のテストは「必須テスト」の名指しを完了条件に入れ、report の対応表で全件を照合する。軽い worker（pi など）は
  受入の E2E を書き漏らし、lint / typecheck を回さず、自分の退行を「既存の失敗」と報告することがあった。「既存の失敗」と書くなら、修正前 commit で同じ失敗が出るログを添えさせる（上の完了報告の条件）。
- worker が実行する安い段・重い段のログが必要な場合は、ログのパスを task 側で決めて明記する
  (`/tmp/<slug>-<name>.log`)。レビュー側がこのログと report の exit code / status・execution・digest を突き合わせて裏取りするので、
  ログは worker に消させない。
- 修正依頼(2 往復目以降)は新規 worker でも追えるよう、`/tmp/<slug>-fix-<N>.md` に
  「前回レポートのパス」「指摘事項」「再検証手順」を書き、
  同じ形式の報告手順を含める。ただし往復ごとに識別できるよう、**レポートパスと報告メッセージに
  ラウンドを含める**こと(前回レポートを上書きさせない):
  - レポート: `/tmp/<slug>-fix-<N>-report.md`
  - route manifest: `/tmp/<slug>-fix-<N>-route.XXXXXX` (前回のものを再利用しない)
