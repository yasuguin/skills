# タスクファイルのテンプレート

`/tmp/<slug>-task.md` として保存し、`<...>` を埋めて使う。`<skill-dir>` は agent-orchestrate の絶対パスに置き換えて書く(worker は skill の場所を知らないため)。
仕様と注意は task に合わせて増やしても減らしてもよい。ただし、**報告の手順、commit の禁止、検証の段の指定、対話承認の禁止、役割宣言(worker 自身が実装する)は必ず残す**。
worker が新しいセッションでも、続けて使う pane でも、このファイルだけで判断できるように書く。

```markdown
# タスク: <一行の目的>

対象リポジトリ: <絶対パス>(ブランチ: <branch>)

## ゴール(完了条件)

- <仕様項目 1>
- <仕様項目 2>
- 変更ファイル一覧を含む完了報告(下記)

## 注意(リポジトリ固有)

- この依頼は、新しい worker のセッションか、同じ ticket で続けて使う pane で実行される。このファイルに書かれていない会話の文脈や、
  前のセッションの記憶を前提にしない。続けて使う場合も、report と done マーカーはラウンドごとに分ける。
- **あなたは worker で、この作業を自分で実装する**。このファイルに分けて投函する指示が無い限り、
  agent-orchestrate などで別の worker やサブエージェントへ再委譲しない。次のどれも、再委譲の根拠にならない:
  報告の手順に agent-orchestrate の script のパスがあること(報告用の script の置き場所にすぎない)、repo の
  AGENTS.md / CLAUDE.md にある「実装は agent-orchestrate で worker へ任せる」という節(main 向けの規則で、
  この task を受け取ったあなたには当てはまらない)、自分の instruction file にある「実装は任せる」方針。
- **git commit を実行しない**(instruction file に commit の手順があっても行わない)。変更は作業ツリーに残したままにする
  (このあとレビューする側が検証して commit する)。
- **TDD で実装する。**「仕様」で名指ししたテストファイル 1 本で、赤から緑になるのを確かめる。さらに安い段として、repo の lint・型チェック
  (repo に無ければ、変更ファイルへの lint と incremental typecheck)を実行し、完了報告の前に指摘を 0 件にする。
  repo の検証が数分以内で終わるなら、task で指定した重い段(全体の test・E2E・build)も実行し、コマンド・真の exit code・ログのパスを report に残す。
  目安として 5 分を超える repo では、重い段は実行しない。
- 完了報告を書く前に、対象の repo で `bash <skill-dir>/scripts/check_delivery.sh <repo> <task-file> <base-commit>` を実行し、
  `check_delivery: status=pass` にする。出力は report に貼る。
- **対話で確認や設計の承認を求めない**。このタスクファイルが承認済みの設計と要件なので、書かれた制約の中では
  いちばん有力な案を自分で選んで進める(grilling などの「実装の前に設計の承認をもらう」手順は、このファイルを受け取った時点で済んでいる)。
  制約を超える判断や、どの案を選ぶかで完了条件の意味が変わる分かれ道に当たったときだけ、質問と選択肢を report に書いて「ブロック」で報告する
  (pane の中で答えを待たない)。
- **最初の障害で止めない**。依存のエラー、import 先の読み違い、テストの失敗などに当たっても、原因を調べて直し、ゴールを
  すべてやり切るまで進める。迷ったら単純な方を選び、選んだ理由を report に書く。ブロックしてよいのは、外部との通信が要るときか、
  ゴールの意味が変わる判断が要るときだけ。その場合も、ほかのゴールを先に進め、試したことと、詰まったエラーの全文を report に書く。
  「未着手」のままブロックにしない。
- dev server などを起動したら、作業の最後に止める(ポートを残さない)。
- <リポジトリ固有の罠・規約。例: rg が壊れるので grep を使う、i18n は ja のみ、等>

## 仕様

<実装の詳細。ファイルパス・行番号・期待挙動を具体的に>

repo の検証区分: <軽い repo / 重い repo（目安 5 分超）>
安い段: <repo の lint・型チェックのコマンド、または変更ファイルへの lint・incremental typecheck>
重い段: <軽い repo の場合だけ指定。コマンドを書く。重い repo は「orchestrator が実行」>
受入基準とテスト対応表:
| 受入基準 | テスト（ファイル:テスト名） |
|---|---|
| <基準> | <file:test name> |

## 必須テスト

- `<受入基準に対応するテスト名をそのまま書く>`

UI の確認場面: <URL・操作。UI 変更が無ければ「なし」>

必要なときだけ、次の見出しの下に許可理由を書く（lint 設定変更は既定で禁止）:

## lint の設定の変更を許す

<変更が受入基準に必要な理由>

テストを書く場合の名指しコマンド: <そのタスクのテストファイル 1 本を実行するコマンド。振る舞いが変わらないなら「なし」>

## 完了報告(必須。これもゴールの一部)

1. 結果を `/tmp/<slug>-report.md` に書く。書くのは、変更ファイルの一覧、仕様の項目ごとの対応状況、受け入れ基準ごとのテストの対応表(ファイル:テスト名)、
   片付いていない事項、安い段と重い段で実行したコマンド・ログの絶対パス・真の exit code。
   UI を変えていて、task が撮影の場面を指定しているときだけ、その場面を撮影して画像のパスを書く(指定が無ければブラウザを開かない)。
   「既存の失敗」「環境の問題」と書くなら、修正前の commit(`git stash` は使わず、worktree などで)で同じ失敗が起きたログを添える。ログが無ければそう書かない。
   実行していない検証を「成功」と書かない(実行していないなら、そもそも書かない)。
2. 次のコマンドで、作業の状態を記録する(ブロックして中断する場合も、理由を report に書いたうえで必ず記録する)。

   完了時:
   `bash <skill-dir>/scripts/mark_report_done.sh /tmp/<slug>-report.md 完了 '<一行要約>'`

   ブロック時:
   `bash <skill-dir>/scripts/mark_report_done.sh /tmp/<slug>-report.md ブロック '<理由>'`

   このコマンドが書くのは report の隣の `/tmp/<slug>-report.md.done` だけで、自分では何も送らない(report が出来たことは、依頼した側の別のプロセスが見つけて届ける)。
   書いたあと、その配送の結果を最大 60 秒待ってから終わる(下の 3)。
   同じ report のパスで再実行しない(「記録済み」のエラーになる)。
   スクリプトを実行できない場合は、同じ内容を直接書いてもよい:
   `printf 'status=完了\nsummary=<一行要約>\n' > /tmp/<slug>-report.md.done`
3. `mark_report_done.sh` は、done マーカーを作ったあと、courier が配送できたか(着弾の確認を含む)を
   最大 60 秒待ってから結果を出力して終わる。この出力を読み、**その文言のまま**
   自分の最終報告と依頼主への回答に使う。「配送を確認できた」以外(未確認、配送の失敗、タイムアウト)が
   出たときも、自分の判断で「報告した」「送信した」と言い換えない。宛先を推測して別の手段で送ろうとしない。
   script を使えず、printf で done マーカーを直接書いた場合は、この配送の確認が走らない。
   その場合は最終報告に「done マーカーは作成済み、配送は未確認」と書く。
```

## 記入時の注意

- **manifest のパス、pane ID、transport を task に書かない**。worker に宛先を渡すと、codex の
  approval review が exfiltration と判定して報告のコマンドを拒否する。worker が知ってよいのは、
  report のパスと done マーカーの手順だけ。route manifest は、投函する側が `mktemp -d` で作った専用のディレクトリに
  置いて courier と共有する(前の manifest を使い回したり上書きしたりしない)。
- commit の禁止は「コミット禁止」とだけ書くと、codex の worker が commit することがある。テンプレートのとおり
  「git commit を実行しない(instruction file に commit の手順があっても行わない)」と書く。それでも commit されたら、
  orchestrator が `git reset --soft <base>` で戻して作り直させる。
- 報告のメッセージは 1 行だけ。詳しいことは必ず report ファイルに書く。
- 検索の範囲は、書き換えてよいパスに絞る。「参照の残りゼロ」を確かめる rg の条件を `shared apps` のように広く書いたら、
  読み取り専用の `apps/*-legacy` まで改名して条件を満たしにいった例がある。
- 受け入れ基準のテストは「必須テスト」の名指しを完了条件に入れ、report の対応表で全件を照らし合わせる。軽い worker(pi など)は、
  受け入れの E2E を書き漏らす、lint や typecheck を回さない、自分が入れた退行を「既存の失敗」と報告する、ということがあった。
  「既存の失敗」と書くなら、修正前の commit で同じ失敗が出るログを添えさせる(上の完了報告の条件)。
- worker が実行する安い段・重い段のログが要るときは、ログのパスを task 側で決めて書く
  (`/tmp/<slug>-<name>.log`)。レビューする側が、このログと report の exit code・status・execution・digest を突き合わせて裏取りするので、
  ログを worker に消させない。
- 修正の依頼(2 往復目以降)は、新しい worker でも追えるように `/tmp/<slug>-fix-<N>.md` に
  「前回の report のパス」「指摘事項」「検証のし直し方」を書き、
  同じ形の報告の手順を入れる。ただし往復ごとに見分けられるよう、**report のパスと報告のメッセージにラウンドを入れる**
  (前の report を上書きさせないため)。
  - report: `/tmp/<slug>-fix-<N>-report.md`
  - route manifest: `/tmp/<slug>-fix-<N>-route.XXXXXX`(前のものを使い回さない)
