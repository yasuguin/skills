# code-as-spec

コード、テスト、型、コード近くのコメントを正本として扱うための document skill。


## Positioning

- **普通の SDD ではない。** 仕様書を正本にして実装を追従させる運用は採らない。spec は一時物として扱い、完了時にコミットの詳細メッセージへ転記して `git rm` する。
- **厳密には BDD ではない。** BDD のように振る舞いを重視するが、Gherkin、Given/When/Then、専用 feature file、ステークホルダー承認フローを必須にしない。
- **TDD に近い。** 変更リスクがある実装では、期待する振る舞いを小さなテストで先に固定し、red-green-refactor で進める。
- **code-as-spec の運用形。** 生きている仕様は、実行されるテスト、コンパイルされる型、実際に読まれるコード、保護された why コメントに置く。

## Roles

媒体ごとに答える問いを分ける。問いが重ならなければ、同じ内容が二か所に書かれることもない。土台は t_wada の「コードには How、テストコードには What、コミットログには Why、コードコメントには Why not」（2017-09-05 のポスト）。

- **コード**: How
- **テスト**: What（public interface から観測できる振る舞い）
- **型 / schema**: 破れない制約（domain rule、入力制約、外部 contract）
- **why コメント**: 現在形の Why / Why not
- **コミットメッセージ**: 変更の Why。diff と一緒に固定されるので古くならない
- **ADR**: 複数の変更にまたがり、3 条件を満たす判断
- **GLOSSARY.md**: 語彙
- **issue / PR**: 作業中の議論・合意・レビューの場。remote にしか残らないので、remote を移すと失われる。便利なので使うが、保管性は repo 内の媒体より低い

why コメントとコミットメッセージは「コードが変わらない限り成り立つか」で分ける。成り立つならコメントに書く。AI エージェントはコードを編集するときにログを引かないので、知らずに触ると壊す情報はコミットだけに置かない。変更時点の経緯はコミットに書き、コメントは現在形で書く（「以前は〜」「〜から変更」はコメントに書かない）。具体的な振り分けは Workflow 1 が正本。

issue / PR にしか無い Why は、remote が変わると消える。main に残るコミットの本文は、issue / PR を開かなくても読めるように書く（squash merge なら squash コミット、merge commit ならブランチ上の各コミット）。`Closes #12` や `Merge pull request #12` だけの本文は、Why が remote にしか無い状態。issue / PR 番号は補助の参照として添える。PR レビューで出た Why not は最も失われやすいので、今も成り立つものは why コメントへ、レビューを受けて変えた理由はコミット本文へ移す。

## Truth Hierarchy

矛盾したら、上から順に正本とする。コミットメッセージと issue / PR は履歴であり正本ではないので、ここには入らない。

1. source code
2. tests
3. types / schemas / public interfaces
4. コード近くの why コメント
5. README / docs / spec docs

source code と tests の食い違いは順位で片付けない。テストは意図した振る舞いを表すので、食い違いは不具合の兆候として扱い、どちらが意図どおりかを確かめてから直す。

docs は無価値ではない。ただし、コードとテストに追従更新し続ける「正本の複製」にしない。

`GLOSSARY.md`（用語集）と `docs/adr/`（ADR）は 5 の docs に属するが、「正本の複製」ではない。用語集はコードのシンボル名から復元できない意味の境界を、ADR はコードに現れない判断の理由を持つ。小さいので追従コストが低く、ADR は書き換えず新しい ADR で supersede するため、追従更新の義務も発生しない。書き方は `domain-modeling` skill の `GLOSSARY-FORMAT.md` / `ADR-FORMAT.md` が正本。

## Core Rules

- 振る舞いは、public interface 経由の test に落とす。
- domain rule、入力制約、永続化 schema、API contract は、型・schema・validator・contract test に落とす。許可値やデフォルトは既存の定数・型から導出し、二重定義しない。
- コードから復元できない判断と制約は該当コードの近くに現在形の why コメントで残し、変更の経緯はコミットメッセージに書く（振り分けは Workflow 1）。
- すべての媒体を日本語で書く。対象はコメント、テスト名（`describe` / `it` の文字列）、コミットメッセージ、issue、PR、ADR、GLOSSARY.md。技術識別子・コード内シンボル・URL はそのまま残す。例外は、既存の英語コードベースへの整合、言語仕様上の識別子、ユーザーの明示指定の 3 つ。
- well-named identifier、型、短い関数で読める what コメントは増やさない。
- 仕様書を書く前に、その情報を test / type / code comment のどこへ置けるかを先に判断する。
- docs を作る場合も、正本ではなく入口、索引、外部契約、利用者向け説明として書く。repo に残してよいのはコード・テスト・型・近接 why コメント、`GLOSSARY.md`、ADR、README などの利用者向け文書だけ。
- AI に読ませる前提の独立ドキュメントを増やさない（確率的に読み落とされる）。AI に確実に届けたい情報ほど、test / type / 近接コメントに置く。

## Temporary Design and Planning Docs

spec・plan・ticket・設計メモ・調査メモ・進捗・migration log はすべて一時物で、正本ではない。手書きの設計 spec（`docs/specs/` など）、`to-spec` / `to-tickets` / `wayfinder` が出す spec・ticket・map（GitHub Issues）が該当する。1 セッションで終わる作業は plan ファイルを作らず、会話の中で整理してそのまま実装する。

- 調査メモや作業メモは最初から repo の外（OS の一時ディレクトリ）に置く。
- issue tracker 上の spec / ticket と PR は remote にしか残らない。閉じる前に、そこにしか無い情報を repo 内の媒体へ移す。今も成り立つ制約は why コメント、変更の Why は main に残るコミットの本文、用語は `GLOSSARY.md`、3 条件を満たす判断は ADR 提案へ回す。全文の転記は repo 内の手書き spec だけで、下の手順で転記して `git rm` する。
- spec とコードがズレたら、コード、テスト、型、近接コメントを正とする。追従更新はしない。
- 完了時は spec / ticket の全文を完了 commit の詳細メッセージに転記してから `git rm` する。履歴に全文が残るので、リポジトリには残さない。

  ```bash
  spec=docs/specs/YYYY-MM-DD-<feature>.md
  msg=$(mktemp)
  { printf '%s\n\n' '<subject>'; cat "$spec"; } > "$msg"
  git rm -q "$spec" && git commit -F "$msg"
  ```

- spec にだけ残っている有用な判断があるなら、必要な部分だけを test / type / code comment / 利用者向け doc に移す。
- 捨てる前に、そこにしか残っていない用語は `GLOSSARY.md` へ、ADR の 3 条件（覆しにくい・文脈なしでは驚く・実際にトレードオフがあった）を満たす判断は ADR として**ユーザーに提案**し、了承されたら `docs/adr/` へ書く。ADR はその場で書かない。
- 用語は設計の会話中に確定した時点で `GLOSSARY.md` に書く（`domain-modeling`）。ADR は 3 条件を満たしたらその時点でユーザーに提案する。完了時の移送はその取りこぼしを拾う保険にすぎない。

## Use This Skill When

- ユーザーが「コードを正本にする」「テストを仕様にする」「spec docs を追従しない」と言う
- 新機能や修正で、仕様をどこに残すべきか迷っている
- spec docs を作る提案が出たが、管理コストやボトルネックを避けたい
- BDD と呼ぶべきか、TDD と呼ぶべきか、code-as-spec と呼ぶべきかを整理したい
- docs/spec を更新せず、テスト・型・コメントで根拠を残す方針を明確にしたい
- 既存コメントを整理・最適化したい
- issue / PR の内容のうち、何をコミット・コメントへ残すか決めたい

## Workflow

### 1. 情報の置き場所を決める

依頼内容を次のいずれかへ分類する。この一覧が「情報の置き場所」の分類の正本。置き場所のルールを変えるときはここだけを直す。


- **実行可能な振る舞い**: test に置く
- **データ形状 / domain rule / 外部 contract**: type、schema、validator、contract test に置く
- **なぜその実装か / なぜ別のやり方をしないか**: コード近くの why コメントに現在形で置く。書いてよいのは、直下のコードからも、grep で 1 回たどれる範囲（呼び出し側・呼び出し先・型・テスト）からも復元できない理由だけ。1 つの理由は 1〜2 行で書く。これが why コメントの基準の正本で、Workflow 4 の振り分けもこれに従う。
  - 復元できるものとみなす: 名前・型・条件式・分岐をドメイン語で読み下した文、誰が呼ぶ・誰が渡す・どこで使うという配線、型で読める値の意味（null・空配列・optional のときの意味）、テスト名で言い切れている振る舞い
  - 基準を満たしやすい形: あえてやっていないこと（例: ここで null チェックしない理由）、採用しなかった代替案、採用 OSS / library の固定理由、外部仕様の罠、障害由来の制約、timeout / retry / batch サイズなど数値の根拠、混同しやすい同名フィールドの区別。この形に当たっても、理由がコードや呼び出し側から読めるなら書かない
- **なぜ今この変更をしたか**: コミットメッセージの本文に置く。変更のきっかけ、以前の実装と変えた理由、見送った選択肢のうち変更時点にしか意味がないもの。コードが変わらない限り成り立つ部分は why コメントにも置く
- **コードから復元できない大きな背景**: README など利用者向け文書に置く。外部 schema 契約（DB field 一覧、API payload）、アーキ全体像、運用情報（認証の使い分け、env var、deploy 経路）のように「他チームに渡す」「コードから復元できない外部運用」が対象。設計メモや release sign-off の記録は一時物なので置かない
- **覆しにくく、文脈なしでは驚き、実際にトレードオフがあった判断**: 3 条件のどれか 1 つでも欠ければ近接の why コメントで足りる。3 条件を満たすときは、その場で書かずユーザーに ADR として提案し、了承されたら `docs/adr/NNNN-slug.md` に 1〜3 文で置く。書式は `domain-modeling` の [ADR-FORMAT.md](https://github.com/mattpocock/skills)
- **ドメイン用語の定義**: `GLOSSARY.md`（glossary）に置く。コードのシンボル名から復元できない意味の境界や avoid リストはここに集約し、実装詳細は書かない。書式は `domain-modeling` の [GLOSSARY-FORMAT.md](https://github.com/mattpocock/skills)
- **一時的な合意や作業計画**: spec / ticket / 設計メモは一時物。完了時に全文をコミットの詳細メッセージへ転記して `git rm` する。調査メモや作業メモは最初から repo の外（OS の一時ディレクトリ）に置く

分類できない場合は、まず test にできるか、次に type にできるか、最後に近接コメントにできるかを検討する。

### 2. 実装は小さな behavior slice で進める

着手前に触る領域の `GLOSSARY.md` と `docs/adr/` を読み、テスト名・型名・関数名の語彙を用語集に合わせ、既存 ADR と矛盾する変更を提案しない。

新しい振る舞いは、ユーザー価値または外部から観測できる単位で切る。

1. 期待する振る舞いを 1 つ選ぶ
2. 失敗する test を書く
3. 最小実装で通す
4. 重複や読みにくさを refactor する
5. 現在形の why / why not は該当コードの近くにコメントし、変更の経緯はコミットメッセージの本文に書く

実装詳細に張り付いた test ではなく、振る舞い、contract、回帰リスクを守る test を優先する。

### 3. docs 作成依頼を受けたら用途を確認する

docs が必要な場合は作る。ただし、次のどれかに限定する。

- 初期導線や全体像
- 外部 API / DB / schema など、コードだけでは外部関係者が読めない契約
- 運用手順、障害対応（運用者向け文書として残してよい。release sign-off の記録は一時物で、PR 本文か repo の外に置く）
- 重要な設計判断の背景（覆しにくい判断は ADR を提案する）

「実装のたびに追従する振る舞い仕様」は docs に置かない。test / type / code comment に移す。

### 4. レビューと既存コメントの最適化で正本の重複を潰す

レビュー時と既存コメントの最適化時は、次を探す。

- docs と test が同じ振る舞いを二重に正本化していないか
- comments が Workflow 1 で「復元できる」とした説明（what の読み下し・配線・型で読める値の意味）を持っていないか
- comments に変更の経緯（「以前は〜」「〜から変更」）が混ざっていないか。経緯の形で書かれた制約（例:「以前は retry していたが二重課金が起きた」）は現在形の why not（「二重課金になるため retry しない」）に書き直して残し、純粋な経緯だけをコミットメッセージへ移す
- あえてやっていないこと（一見足りない処理）に why コメントがあるか
- why コメントや外部仕様の罠が削られていないか
- test が private implementation に寄りすぎていないか
- 型や schema で守れる rule を自然言語だけで管理していないか

重複がある場合は、docs を厚くするのではなく、正本を code / test / type / comment へ寄せる。

既存コメントの最適化は、上の観点で対象範囲のコメントを 1 つずつ次のどれかに振り分ける。対象範囲のすべてのコメントを振り分け終えたら完了。

- **残す**: Workflow 1 の基準を満たす現在形の why / why not。迷ったら理由の部分を残す側に倒す
- **書き直す**: 説明と理由が混ざったコメントは、理由だけの 1〜2 行にする（例:「帯は承認待ちでなくなると消える。送信中は出さない（送信中は採否を止めるので、別の追加指示は送れない）」→「送信中は採否を止めるので、別の追加指示は送れない」）。経緯の形で書かれた制約を現在形にする。repo の外にしか無いものへの言及（issue / PR 番号、repo に無い試作・要件メモ、口頭の経緯）は、repo 内の指し先（実装ファイル、ADR 番号）に置き換えるか外す。外すと理由が消えるなら、理由のほうを現在形で書く
- **削除する**: Workflow 1 で「復元できる」とした説明だけのコメント（直下のコードや prop 名の言い換え、短い関数の要約、配線、型で読める値の意味）、純粋な経緯、すぐ上のコメントと同じことを言う重複
- **修正する**: コードと食い違うコメント。コードを正としてコメントを合わせる
- **追加する**: 理由の書かれていない「あえてやっていないこと」

「修正する」は最も見落としやすく、実際には最も多い。読むたびに次の 4 つの型を疑う。

- **指し先切れ**: コメントが挙げるファイル名・定数名・関数名・ADR 番号・数値（秒数、件数、上限）が今のコードに無い、または違う。名前と数値は `git grep` で実在と値を確かめる
- **位置ずれ**: 説明している宣言から離れた位置にある（コードの移動や挿入で、別の宣言の上に取り残された）。説明している宣言の直前へ移す
- **旧語**: 改名前の名前や、`GLOSSARY.md` の _Avoid_ に挙がっている語が残っている。改名の一括置換で文の意味が壊れたもの（「旧 `/new-name/...` は転送しない」のように新旧が入れ替わった文）もここに入る
- **範囲の取り違え**: 「4 つの領域」「markdown だけ比べる」のように、数や対象がコードの今の範囲と合わない

「追加する」は、次のどれかに当たり、かつ理由をコード・テスト・ADR・`GLOSSARY.md`・その行の `git log -L` / `git blame` で確かめられたときだけ書く。

- 一見足りない処理: retry しない、null チェックしない、await しない、意図的な空の catch・`.catch(() => undefined)`、エラーを握り潰す
- 根拠が要る数値: timeout、上限、batch サイズ、遅延、マジックナンバー（例: 960×720 が 4:3 の実寸であること）
- 順序や待ち方に意味がある処理、ライブラリや外部仕様の挙動に依存する処理（例: ライブラリの API が設定値で丸めないこと）
- テストでは、なぜその前提・fixture・待ち方にしたか（例: 即答する fake を route で保留して処理中の状態を作る）

同じファイルで同じ形が繰り返すなら、理由は最初の 1 か所に書けば足りる。理由を確かめられない数値や処理には、推測でコメントを足さず報告に挙げる。

範囲の既定は、明示的に依頼されたら指定範囲の全体、ほかの作業中なら変更するコードに付いているコメントだけ。repo 全体のように範囲が広いときの分割・検証・コミットの進め方は [references/comment-sweep.md](references/comment-sweep.md)。

- 理由を確かめられないコメントは書き換えずに残し、報告に挙げる。理由を推測で作らない。
- コメントの形をしたコードは振り分けずにそのまま残す。`eslint-disable`、`@ts-expect-error`、`biome-ignore`、`noqa` / `type: ignore`、`FORK(<tag>):` マーカー、ライセンスヘッダ、自動生成ファイルが該当する。公開 API の doc コメントは、what だけでも削除しないが、コードと食い違っていれば修正する。
- 英語のコメントを日本語に訳すのは、日本語を慣習とする repo だけ。英語コードベースのコメントや、他 repo から持ち込んで追従しているコードのコメントは英語のまま最適化する。
- 振る舞いの変更とは別の、コメントだけのコミットにする。削った経緯の要点はそのコミットの本文に書く。最適化中に見つけたバグや未使用コードは同じコミットで直さず、報告に挙げて別のコミットで直す。

## Non-Negotiables

- spec docs を正本にする普通の SDD を提案しない。
- `docs/spec/*.md` のような仕様書を、実装ごとに追従更新する義務にしない。
- BDD と呼ぶ場合は、厳密な BDD ではなく「BDD 的に振る舞いを重視する」と説明する。
- Gherkin や feature file を必要条件にしない。
- コードから復元できない現在形の why / why not コメントを「冗長」として削除しない。
- test を実装詳細の固定具にしない。
- spec・plan・ticket・設計メモ・調査メモ・進捗・migration log を repo に残さない。「古い作業メモとして無視してよい」「残してよい」は認めない。
- docs を消す場合は、コードから復元できない情報が test / type / comment / 残すべき doc に移っていることを確認する。
- GLOSSARY.md（glossary）と docs/adr/（Architecture Decision Records）は削除しない。これらはコードから復元できないドメイン知識と意思決定の背景であり、code-as-spec が排除する「追従義務のある仕様書」とは異なる。

## Naming Guidance

この方針の名前を聞かれたら、既定では `code-as-spec` を推奨する。

- `code-as-spec`: 最も正確。コード、テスト、型、コメントを正本にする方針が伝わる。
- `bdd`: 一般には意味が広く、Gherkin や Given/When/Then を期待させやすい。今回の名前としては避ける。
- `behavior-as-spec`: 振る舞い重視は伝わるが、型や why コメントまで含む正本方針としては少し狭い。
- `executable-spec`: test と type には強いが、コードコメントに残す設計判断が抜けやすい。
- `living-spec`: 良いが、spec docs を生かし続ける運用にも見えるため、今回の意図では曖昧。

## Output Style

ユーザーには、次を短く返す。

- 今回の情報は `test` / `type` / `comment` / `commit` / `adr`（提案） / `glossary` / `doc`（利用者向け） のどこへ置くべきか
- spec docs を避ける理由
- spec / ticket / 作業メモを使う場合は、それが一時物であり正本ではないこと
- 必要なら TDD で最初に固定する behavior
- docs を残す場合は、その docs が正本ではなく何のための入口か
