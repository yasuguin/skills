# Trigger Signals

## 強い signal

- ユーザーが明示的に「skill にして」「skill に反映して」「今後はそうして」と言う
- ユーザーが「いったんコミットして比較してから skill を直して」と言う
- 同じ correction が 2 回以上入る
- 完了報告後に「push まで」「反映まで」など scope の追加が入る
- 既存 skill の命名や description が実運用とずれている
- typo や重複名のような運用ノイズが継続している
- predeploy / review / audit 系 skill を通したのに、実害のある見逃しが起きた。
  対象 skill の完了条件と eval を更新する（具体パターンはその skill の references / evals に置く）
- ユーザーが「そういうふうに網羅的にやるんだよ」と、より厳しい粒度の進め方を今後の既定にしたいと明示した

## 中程度の signal

- 毎回確認しているが、本来 workflow に入っているべき質問がある
- 毎回手で diff を読んでから同じ判断をしている
- 毎回その場の手編集差分を見ながら skill を直していて、証拠コミットと skill 修正コミットが混ざる
- 毎回同じ種類の確認をしていて、ユーザーから「そこはもう聞かなくてよい」と止められる
- 特定ファイルの更新漏れ、eval 漏れ、同期漏れが繰り返される
- ユーザー固有ルールではなく repo 全体の運用ルール変更だと分かる
- skill に逃がした結果、頻繁に使う行動規範まで本文から消えて不便になっている
- 対象 skill の確認粒度が繰り返し漏れる
- 新しく AGENTS.md/CLAUDE.md や hook にルールを追加したら、既存 skill に同じ判断基準の重複記述が残っている

## skill 化しないほうがよいもの

- 今回だけの例外対応
- 一時的な環境故障への回避策
- そのユーザーだけの好みで、他ケースに一般化すると壊れるもの
- 根拠が弱く、期待仕様として固定すると危険なもの
- 高頻度で参照する基本動作
- エージェントの根幹挙動を決める既定

## 変更方針の見極め

- description を直す:
  - trigger の漏れや誤発火が問題のとき
- GOAL / PRIMARY RULES を直す:
  - 完了条件や必須動作が足りないとき
- workflow を直す:
  - 順序や承認ゲートが抜けていたとき
  - 不要な確認が多く、既定で進めてよい条件を明文化すべきとき
  - 見た目の成功シグナルだけでなく、実際の contract 達成を確認する手順が必要なとき
- references を足す:
  - 長い判断基準や mapping が必要なとき
- evals を足す:
  - 同じ失敗を再発させたくないとき
  - 実害のある見逃しを再現 prompt として固定したいとき
  - よい粒度の成功パターンを既定化したいとき
- instruction file へ戻す:
  - skill 化しすぎで、日常の振る舞いまで外へ逃げてしまったとき
- 統合する・削除する:
  - 同じ判断基準が skill 本文・AGENTS.md/CLAUDE.md・hooks・他 skill の複数箇所に重複しているとき
    （スコープと詳細度で正本を 1 つ決め、他は参照 1 行へ縮約するか削除する。全プロジェクト共通の
    一般則なら AGENTS.md/CLAUDE.md、詳細な判断基準なら該当 skill、機械検知できるなら hook が正本の
    候補になる。固定の優先順位ではなく都度判断する）
  - 加筆を重ねた結果、現在の best practice と矛盾する・もう使われていない記述が残っているとき
