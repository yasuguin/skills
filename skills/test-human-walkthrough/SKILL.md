# test-human-walkthrough

架空のユーザーとしてアプリを「普通に使う」ことで、コードを読むだけでは見えない違和感を拾う。
役割の目での精査や、変更箇所だけの確認とは目的が違う。
ここでは、初めて触る人がつまずく所、操作と表示の食い違い、裏で壊れているロジックを、
実際の操作の流れの中で見つける。

範囲は**報告まで**。コードは直さず、Issue も作らない。ただし報告はたいてい Issue 化されるので、
各項目を 1 件ずつそのまま Issue にできる粒度で書き、添付に使うスクリーンショット・画面録画も
**調査の最中に**撮っておく（後から同じ状態を作り直すのは難しく、再現しないこともある）。

ブラウザ操作の手順そのもの（claude-in-chrome のツールの読み込み・タブ・console・dev server の起動と停止）は、
使っている環境の手順に従う。ここでは重ねて書かない。
対象が macOS のネイティブアプリ（メニューバー常駐アプリなど）なら、claude-in-chrome の代わりに
[references/native-macos.md](references/native-macos.md) の手段で操作・撮影する。手順 1〜5 の流れは同じ。
つまずきやすい点は [references/gotchas.md](references/gotchas.md) を、作業を始める前に一度読む。

## 実行の分担

Claude Code では、手順 1 をメインの会話で行い、手順 2〜5 を、コードを直す道具を持たない agent（Edit・Write を外した
subagent の定義）に渡す。触っている最中に直してしまうことがない。
一方でユーザーに話しかけられないので、ペルソナの提示と録画の注意は渡す前にメインで済ませる。

- 渡す prompt に書くもの: 対象 URL（ネイティブアプリならアプリ名と起動中の .app のパス）、
  dev server やアプリを自分で起動したか、ペルソナとシナリオ、証拠の置き場、
  この SKILL.md のパス（agent はそれを Read して手順 2〜5 に従う）。
- 返ってきた報告をユーザーに伝える。Issue 化を頼まれたら、それもメインで行う。
- agent を使えない環境（Codex など）では、手順 1〜5 をすべて自分で行う。

## 1. 準備

1. 対象アプリと URL を確定する。dev server が既に動いていればそれを使い（`lsof -nP -iTCP -sTCP:LISTEN`
   とプロセスの cwd で対象 repo のものか確かめる）、止めない。無ければ自分で起動し、
   最後に自分で止める。
2. README・マニュアル・`GLOSSARY.md` から、想定利用者と主な用途を読む。
3. **ペルソナとシナリオを決めてユーザーに 1 回だけ見せる**。ペルソナは 1〜2 行
   （例:「企画職。ITは普通。今日は手元の資料からスライドの構成案を作りたい」）、シナリオは 5〜8 個の
   やりたいこと（初見の印象 → 主要タスクを最後までやり切る → 周辺ページ → 設定・管理 → 検索や
   ショートカット）。ユーザーが指定済みならそれに従い、異論が無ければそのまま進める。
   画面録画は Chrome のウィンドウだけを撮る（他のウィンドウや通知は写らない）。録画中は対象タブを
   そのウィンドウの前面のタブにしておき、ウィンドウを別スペースへ移したり最小化したりしないよう、
   この 1 回で一緒に伝える。
   ネイティブアプリは、ユーザーの画面とキーボードをそのまま借りて操作する（ブラウザのように裏のタブで
   完結しない）。この 1 回で、操作中は Mac に触らないことと、対象を出す場所（専用の Space か、全画面の
   ターミナルを解除したデスクトップ）を用意してもらうことも伝える。渡す前に、対象のウィンドウと
   メニューバー項目が画面上にあるかをメインで確かめる（手順は native-macos.md の「渡す前の確認」）。
4. 証拠の置き場を決める: `/tmp/test-human-walkthrough/<YYYYMMDD-HHMM>/`。対象 repo の中には置かない
   （作業ツリーを汚さない）。

## 2. 人間として一操作ずつ触る

ペルソナの目的を達成しようとして、迷ったら迷ったまま進む。迷ったこと自体が所見になる。

- **操作は人間と同じ経路だけで行う**。スクリーンショットを見て座標をクリックし、キーボードで入力する。
  JavaScript でクリック・値の注入・状態の書き換えをしない（それをすると、人間が詰まる所を素通りする）。
  `javascript_tool` は観測専用（`document.activeElement`、`elementFromPoint`、computed style、rect）。
  ネイティブアプリでも同じで、見えている要素を System Events や CGEvent でクリック・キー入力し、設定ファイルを
  直接書き換えて状態を作らない。AX 属性の読み取りは観測として使ってよい。
- **操作ごとに見る**。押したら画面がどう変わったかを確かめてから次へ進む。予想と違ったら、その瞬間に
  所見 ID（`F01`, `F02`, …）を振って 1 行メモする（画面 / やったこと / 期待 / 実際 / 証拠ファイル）。
- **所見ごとに、その場で証拠を残す**。Issue に貼ったとき、本文を読まなくても何が起きているか分かる
  ものを選ぶ。
  - 静止画で伝わるもの（折り返し・揃わない・文言・エラー表示・空状態）: その画面を
    `save_to_disk: true` で撮る。小さい所は `zoom` の `save_to_disk` で寄りも撮る。
  - 流れやタイミングが要るもの（押しても反応しない、一瞬だけ出て消える、状態が後から食い違う、
    二重に動く、フォーカスが飛ぶ）: 最初から動画で撮る。GIF（`gif_creator`）は使わない。操作ごとの
    スクリーンショットをつないだコマ送りになり、一瞬だけ出る表示や待ち時間の長さが残らないため。
    macOS の `screencapture -l`（ウィンドウ ID 指定）で Chrome のウィンドウだけを録画し、Issue に貼れる MP4 にする
    （コマンドは [references/gotchas.md](references/gotchas.md) の「画面録画」）。気づいた時点で
    録画していないのが普通なので、再現手順を 1 回やり直しながら録る。再現しなければ静止画と
    「1 回だけ発生」のメモを残し、要確認 にする。
  - 録画はセッション全体ではなく所見 1 件ごとに区切り、数秒〜30 秒に収める（GitHub の動画添付は
    無料プランの repo で 10MB まで。長い動画は Issue で見てもらえない）。
  - 取得したファイルは証拠の置き場へ `F03-<短い説明>.png` / `.mp4` の名前で置く。同じ原因の所見を
    まとめたら、証拠もまとめた先の ID に寄せる。
  - 他人の個人情報・トークン・社内の機密が写り込んだら、その証拠は使わず撮り直す。
- **待つときも人間と同じように見る**。エージェントの応答・読み込み中の表示・途中経過を、
  まとめた wait + 縮小スクリーンショットで追う。終わってからの最終状態だけで判断しない。
- **周辺も一通り踏む**。サイドバーの各ページ、戻るリンク、モーダルの開閉と Escape、行メニュー、
  ツールチップ、検索パレット、設定・管理画面。同じ概念が別の場所でどう表示されるか（名前・アイコン・
  トグルかチェックボックスか）を見比べる。
- 長い作業になるので、区切りごとにユーザーへ「今どこを見ているか」を 1 文で伝える。
  サブエージェントとして動いているときはユーザーに届かないので、この 1 文は省く。

## 3. 裏取りする

画面で見えたことを、そのまま原因と書かない。種類ごとに裏を取ってから所見にする。

- **ロジック系**（状態が食い違う、作ったものが消える、二重に動く）: 永続データ（イベントストア・DB・
  ワークスペースのファイル）、プロセスの起動時刻、git の状態を読み、時系列で何が起きたかを並べる。
  アプリやエージェント自身の説明（「サーバーが再起動したため」など）は鵜呑みにせず、事実で確かめる。
- **UI のズレ**（折り返し、揃わない、太さが違う）: ソースのコンポーネントとクラスを読み、原因の
  クラスまで特定する。ソースで決まらないときだけ実測する。
- **仕様かもしれないもの**（Enter が改行になる等）: ソースのコメントや設定で意図を確かめる。
  仕様なら「不具合」ではなく「気づきにくい」という UX の所見に書き換える。
- 所見には **確認済み / 要確認** を付ける。一度しか起きず原因も追えなかったもの、
  自動操作の副作用が疑われるものは 要確認 か、報告から外す。

## 4. 報告する

日本語で、次の順に書く。

1. **ロジック（重要度順）** → **UX** → **見た目・文言**。各項目に所見 ID、確認済み / 要確認、
   根拠（データのパス・イベント番号・`file:line`）、再現手順、証拠ファイルのパスを付ける。
   原因を特定していないものは断定せず、「調べる場所の候補」として書く。
2. repo やユーザーのデザインルール（`DESIGN.md` など）に反する点は、
   どのルールに反するかを明記する。
3. **未確認の範囲**（触っていない機能・画面幅・ダークモードなど）。
4. **副作用**（作ったデータ・押した承認・採番された ID・止めた／止めていないサーバー）。
5. **証拠の一覧**: 置き場のディレクトリと、所見 ID → ファイルの対応。証拠が無い所見はその理由
   （再現しなかった、ソースで確定した等）を書く。証拠は Issue の添付に使うので、見せる 1 枚に絞らず残す。
   Issue 化を頼まれたら、画像・動画は Issue に添付する。

些細な点も省かずに挙げる。ただし同じ原因から出た症状は 1 項目にまとめる。

## 5. 後片付け

- 自分が開いたタブを `tabs_close_mcp` で閉じる。
- 自分が起動した dev server だけ止める（ユーザーが起動していたものは止めない）。
- 確認用に作ったデータと証拠の置き場は消さずに報告へ残す（消すかどうかはユーザーが決める）。
