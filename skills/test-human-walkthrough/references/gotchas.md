# gotchas

実際のセッション(2026-09-29)で踏んだ点。

## ブラウザ接続

- `tabs_context_mcp` が "Browser extension is not connected" を返し、`list_connected_browsers` が空なら、
  再試行しても変わらない。`pgrep -fl chrome-native-host` で中継プロセスの有無と、Chrome の PID が
  前回と同じか(= 再起動されていないか)を見てから、ユーザーに次を案内する:
  `/chrome` で再接続 → だめなら Chrome を ⌘Q で完全終了して起動 → 拡張に Claude Code と同じ
  アカウントでログイン。同じ状態のまま再試行を繰り返さない。
- 作業の途中で接続が切れることがある。切れたら、ソースで確かめられる項目はソースで進め、
  実機での再計測が要る項目は「実機未計測」と明記する。

## スクリーンショット

- devicePixelRatio が 1 でない環境では、最初の 1 枚が 2×2 のタイル状に崩れることがある。
  撮り直せば直るので、所見にしない。
- 見るだけのスクリーンショットは `scale` 0.5〜0.6 で撮る。文字を読む必要がある所だけ `zoom` する。
  証拠として保存する 1 枚は `scale` を下げない（Issue で文字が読めなくなる）。

## 画面録画(screencapture)

GIF(`gif_creator`)ではなく、macOS の `screencapture` で最初から動画として撮る。
画面の範囲(`-R`)ではなく、ウィンドウ ID(`-l`)を指定して Chrome のウィンドウだけを撮る。
`-R` は他のウィンドウ・通知・デスクトップがそのまま写るうえ、`osascript` の `bounds` と
座標系がずれて(複数ディスプレイで実測)タブバーが切れた。`-l` の出力はそのウィンドウの中身だけで、
別ディスプレイや他アプリは入らない(2026-10-01 実測。H.264 の .mov、1920×1080 で出た)。
他のウィンドウが前面に重なったときも写らないかは未実測なので、最初の 1 本で確かめる。

1. ウィンドウ ID を取る(録画の直前に毎回。ウィンドウを動かすと ID も対象も変わる):
   `WID=$(swift scripts/window-id.swift "Google Chrome" "<タブのタイトルの一部>")`
   ウィンドウ名はアクティブタブのタイトルなので、録画したいタブを前面のタブにしてから取る。
   標準エラーに選んだウィンドウ名が出るので、対象と合っているか見る。見つからないときは、
   Chrome が別スペース・最小化で画面上に無い(このときは録画もできない)。
2. 録画をバックグラウンドで始め、再現操作をする:
   `screencapture -x -v -V 30 -k -C -o -l"$WID" <置き場>/F03-raw.mov`
   (`-V` は秒数の上限、`-k` はクリック表示、`-C` はカーソルも撮る、`-o` はウィンドウの影を
   付けない、`-x` は音を鳴らさない)。Bash の `run_in_background` で起動し、終わりを待つ。
   `-V` を省くと止め方が無くなるので必ず付ける。
3. Issue 用に縮小して MP4 にする:
   `ffmpeg -v error -y -i F03-raw.mov -vf "scale=iw/2:-2" -c:v libx264 -crf 28 -preset veryfast -pix_fmt yuv420p -movflags +faststart -an F03-<短い説明>.mp4`
   (2 秒の試し撮りで 1.4MB → 95KB)。10MB を超えたら撮り直して短くする。
4. 撮れているかは、`ffmpeg -ss <秒> -i F03-….mp4 -frames:v 1 F03-check.png` で 1 フレーム抜いて見る。
   最初の 1 本は必ず確かめる(別のウィンドウを撮っていないか、他のものが写り込んでいないか)。

- 録画中にユーザーがウィンドウを動かしたりサイズを変えたりすると、スクリーンショットの座標の
  基準も変わり、クリックが別の要素に当たる(2026-10-01 実測)。操作のたびに撮り直した
  スクリーンショットの座標を使い、続けてずれるならブラウザ操作を止めてユーザーに確認する。
- ウィンドウが他のウィンドウの裏にあると、ページは `document.visibilityState === "hidden"` になり、
  react-query などのポーリングが止まって表示が遅れる(2026-10-01、承認カードが約 40 秒遅れた)。
  表示の遅れを所見にする前に、`javascript_tool` で `document.visibilityState` を確かめる。
- ターミナルに「画面収録」の権限が無いと失敗する。そのときは ユーザーに システム設定 → プライバシーと
  セキュリティ → 画面収録 で許可してもらい、許可されるまでは静止画の連番で代える旨を報告に書く。

## 入力

- contenteditable(ProseMirror / tiptap など)のコンポーザーは、クリック位置によってはフォーカスが
  入らず、`type` した文字が消える。入力前後に `document.activeElement` を確かめる。
  入らなかった場合は `elementFromPoint` で何がクリックを受けたかを記録する。人間も同じ所で
  つまずくので、それ自体が所見になる。
- 送信キーがアプリ固有(Cmd+Enter など)のことがある。Enter で送れなかったら、所見にする前に
  ソースで仕様を確かめる。

## 自動操作の副作用

- 合成 hover でアイコンを素早く移動すると、ツールチップが前の要素のまま残って見えることがある。
  `aria-label` が要素ごとに正しければ、自動操作の副作用として 要確認 に留める。
- `javascript_tool` の戻り値の一部が "[BLOCKED: Cookie/query string data]" に置き換わることがある。
  その場合は、取り出す値を属性・数値などに絞って取り直す。

## console の読み方

- `read_console_messages` の `onlyErrors` は、同じ例外のスタックトレースを毎回全文で返す
  (2026-10-05、Monaco の例外 60 件で数万トークンを使った)。最初は `limit: 5` で例外の種類を
  見て、件数と時刻が要る種類だけ、`pattern` をその例外名に絞って読む。

## ロジックの裏取り

- アプリやエージェントが「サーバー再起動のため」などと説明しても、プロセスの起動時刻
  (`ps -o lstart -p <pid>`)で確かめる。実際は再起動しておらず、別の原因(lease 期限切れなど)
  だったことがある。
- 「完了」「作成しました」と表示されたファイルが、実際に存在するかを `find` で確かめる。
  表示とディスクの状態が食い違うのは、重大な所見になりやすい。
- イベントストアがあれば、seq・時刻・turnId を並べた時系列表を作ってから所見を書く。
  同じ ID の開始イベントが 2 回ある、中断後にも同じ ID のイベントが届く、などの異常が見える。
- URL を開くだけで ID が採番されるような挙動は、永続化されたか(データに残ったか)まで確かめて
  から所見にする。

## 範囲

- 操作中に見つけた不具合を、その場で直しに行かない。原因の深掘りも「修正方針の判断に必要な
  深さ」で止め、調べる場所の候補として報告に書く。
